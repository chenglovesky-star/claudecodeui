# 讯飞数据仓库 SQL 查询

## 使用前提

本 Skill 依赖**当前项目根目录**下的 `./memory/` 目录。

每次执行时自动自检（第一阶段 Step 1）：
- `./memory/MEMORY.md` 不存在 → 自动按 [memory-guide.md](references/memory-guide.md) 分层模板初始化
- `./memory/MEMORY.md` 存在但格式为旧版（无业务目录表格） → 提示用户执行迁移，或按需自动迁移

不同项目目录的 memory 相互隔离。切换 Claude Code 工作目录时，Skill 自动读取新目录的 memory。

> **💡 越用越聪明的秘诀**
>
> 本 Skill 采用**以文件为主的本地记忆**机制：每次查询发现的业务口径、表结构映射、操作码关联，都会积累到 `./memory/` 目录下。记忆越丰富，下次查询跳过搜索的概率越高，速度越快、结果越准。
>
> **如何让它更聪明**：
> - 每次查询结束后，按提示将新发现的口径写入本地记忆（第六阶段）
> - 同一个项目目录下持续使用，知识会在 `biz_*.md` 文件中自动积累
> - 将验证过的口径同步到中心知识库（`saveSqlGuide`），团队所有人都能受益
> - 若发现记忆中有错误口径，随时告知 AI 更新，避免错误传播

## 核心原则

**双 Agent 交叉验证**：两个 subagent 完全独立工作，各自调用 MCP 工具搜索表、查结构、写 SQL、执行。主 Agent 不预查表结构，不提供具体表名或字段，只提供原始需求、记忆中的通用知识和 SQL 规范。

## 工作流程

### 第一阶段：准备轻量上下文（主 Agent）

主 Agent **不调用任何 MCP 查表工具**（searchTables、describeTable 等），只做：

1. **Skill 自检（执行任何操作前）**
   - 检查 `./memory/MEMORY.md` 是否存在：
     - **不存在（首次使用）** → 按 [memory-guide.md](references/memory-guide.md) 新版分层模板自动初始化，并在查询开始前向用户展示以下一次性提示（**不等待用户回复，直接继续查询流程**）：
       ```
       📚 首次在此目录使用 /iflytek-sql-query

       已自动初始化记忆目录 ./memory/。

       这个 Skill 会越用越聪明——每次查询发现的表结构、操作码、业务口径都会
       积累到 ./memory/ 下，下次同类查询可跳过搜索步骤，更快更准。

       建议：在同一个项目目录下持续使用，让知识不断积累。
       切换目录后记忆隔离，需重新积累。
       ```
     - **已存在** → 静默继续
   - 检查 `./memory/general.md` 是否存在：不存在则初始化（含决策树和歧义词表）
   - MCP 连通性验证：调用 `listCatalogs`，失败则告警"MCP 连接异常，查询可能失败"后继续
   - **Hooks 配置检查（强制，未配置时阻断查询）**：读取 `~/.claude/settings.json`（用户全局）和 `.claude/settings.json`（项目级），检查是否存在针对 `mcp__iflytek-sql-gateway__executeQuery` 的 PostToolUse hook：
     - **已配置** → 静默继续，hook 将在每次查询后自动注入强制提醒
     - **未配置** → **立即阻断查询流程**，不得继续派发 subagent，必须先完成配置：
       1. 向用户说明：「检测到未配置 executeQuery PostToolUse hook，该 hook 是保障第六阶段 AskUserQuestion 强制调用的唯一外部机制，未配置将导致记忆系统无法可靠运行。」
       2. 调用 AskUserQuestion 工具询问（必须调用工具，不得文字提问）：
          ```
          AskUserQuestion(
            question="未检测到 executeQuery hook 配置，该配置是强制记忆评估的技术保障。是否现在立即配置？",
            options=["立即配置（推荐）", "跳过（接受记忆系统可能失效的风险）"]
          )
          ```
       3. 用户选「立即配置」→ 读取 `~/.claude/settings.json`，合并写入以下 hook，配置完成后继续查询：
          ```json
          {
            "hooks": {
              "PostToolUse": [{
                "matcher": "mcp__iflytek-sql-gateway__executeQuery",
                "hooks": [{
                  "type": "command",
                  "command": "echo '{\"hookSpecificOutput\":{\"hookEventName\":\"PostToolUse\",\"additionalContext\":\"【强制记忆评估 - 不可跳过】executeQuery 已完成。你现在必须：1）评估本次查询是否有可复用知识（操作码/口径/踩坑/表字段）；2）如有新知识，必须调用 AskUserQuestion 工具询问用户是否写入记忆，严禁用文字提问替代工具调用。\"}}'",
                  "timeout": 5
                }]
              }]
            }
          }
          ```
       4. 用户选「跳过」→ 在 `./memory/general.md` 末尾追加标记 `<!-- hooks-skipped -->` 并继续查询，第六阶段末输出警告：「⚠️ 当前未配置 hook，AskUserQuestion 调用依赖模型自觉性，存在漂移风险。」
2. **读取记忆** — 读 `./memory/MEMORY.md` 和 `./memory/general.md`，提取通用知识（工具限制、性能陷阱）
3. **精确摘取记忆上下文（非全文注入）** — 对需求文本提取核心关键词（业务名 + 操作类型），在命中的 biz_*.md 中逐行匹配：
   - 命中行连同前后各 1 行一起提取
   - 每条标注来源类型：`[操作码口径 | opcodes.md]`、`[陷阱 | core.md]`、`[模板 | templates.md]`
   - **注入体积上限：800 字符**，超出时优先保留操作码和陷阱类条目
   - 不命中任何业务文件时，仅注入 general.md 的工具限制和决策树
4. **知识库检索（主 Agent 专用，subagent 无需重复）** — 调用 `searchSqlGuides`，将需求拆解为 3~5 个核心关键词，每词调用一次，总调用数 ≤ 6 次。此工具为知识库搜索，不属于"查表工具"，主 Agent 可调用。
   - 命中质量评估（影响后续搜索预算）：
     - **高质量**：需求 ≥80% 匹配，有可直接改写的 SQL 模板 → 后续表搜索预算 ≤ 5 次
     - **中质量**：场景相似但口径细节不同 → 后续表搜索预算 ≤ 10 次
     - **未命中**：无相关结果 → 后续表搜索预算 ≤ 20 次
5. **继承对话业务背景** — 若本次对话已有前置需求（如上一个问题是"社区皮肤帖"），则在 subagent prompt 的【需求】块中补注：`【业务背景：本次与上一需求同属 XX 场景，范围限定为 XX】`
6. **歧义词前置确认（必须，派发前执行）** — 读取 `./memory/general.md` 中的【歧义词表】章节，扫描需求文本中是否出现表中的"多义词"列。命中任一词则用 AskUserQuestion 向用户确认后再派发。新发现的歧义词追加到 general.md 歧义词表，无需修改本 SKILL.md。

   若需求表述明确无歧义，可直接跳过此步。

7. **组装 subagent prompt** — 参见下方模板。关键：
   - 【记忆上下文】填入精确摘取结果（≤800字符），标注来源类型
   - 【搜索预算】根据命中质量动态填入（5/10/20）
   - 【paimon/hive 决策树】固定从 general.md 复制，每次都注入
   - searchSqlGuides 已由主 Agent 完成，在 subagent prompt 中明确写"无需重复调用"
8. **置信度评估与路径决策**

同时满足以下全部条件时，走**快速路径**，否则走**标准路径**（双 Agent）：
1. 知识库高质量命中（≥80% 匹配）且有可改写的 SQL 模板
2. 需求与模板的差异仅为参数（日期范围、UID 列表、统计周期等）
3. 记忆中已有该业务的核心表和操作码

**快速路径流程**：
1. 主 Agent 基于模板改写 SQL（填入具体参数）
2. 若涉及大表（ods_ime_operation_log 或分区范围 > 30 天），先执行探针查询：
   ```sql
   SELECT COUNT(1) AS cnt FROM {目标表} WHERE {分区条件} LIMIT 1
   ```
   结果 > 5000 万行时，提示用户缩小范围，不直接执行完整 SQL。
3. executeQuery 执行完整 SQL
4. 直接进入后验层（技术合理性检查 → 业务合理性校验 → 展示）

快速路径不启动 subagent。

### 第二阶段：并行派发（两个 subagent）

> **验证目标声明**：双 Agent 验证的目标是**执行层一致性**（在给定记忆上下文前提下，SQL 技术实现是否正确且一致），而非业务判断独立性。两个 Agent 共享记忆上下文起点，各自独立完成表结构探索和 SQL 编写。业务口径正确性由预检层（记忆质量门控）和后验层（合理性校验）保障。

使用 Agent 工具在**同一条消息**中并行派发两个 subagent（subagent_type: "general-purpose"）。

**subagent prompt 模板：**

```
你是一个数据分析 SQL 专家。根据需求，自主使用 MCP 工具完成从表搜索到 SQL 执行的完整流程。

【需求】
{用户原始需求，原文粘贴}

【记忆上下文】
{主 Agent 从 biz_*.md / general.md 中提取的相关条目，可直接复用，无需再搜索已知信息}

【MCP 工具】
1. mcp__iflytek-sql-gateway__searchSqlGuides(keyword) — 知识库检索（主 Agent 已完成，subagent 无需调用）
2. mcp__iflytek-sql-gateway__searchTables(keyword, catalog?, database?) — 按关键词搜索表
3. mcp__iflytek-sql-gateway__searchTablesByColumn(keyword) — 按字段关键词搜索表
4. mcp__iflytek-sql-gateway__searchTablesByEnum(keyword) — 按枚举含义反查表和字段
5. mcp__iflytek-sql-gateway__describeTable(tableName, database, catalog) — 查看表结构
6. mcp__iflytek-sql-gateway__searchEnumByColumn(tableName, database, catalog, columnName) — 查看字段枚举值
7. mcp__iflytek-sql-gateway__executeQuery(sql, maxRows) — 执行 SQL（仅 SELECT，最大 5000 行）

【数据仓库环境】
- Catalogs：default_catalog、paimon、hive
- 日期分区字段：通常为 dt 或 proc_date，格式 yyyymmdd
- 执行引擎：Flink SQL 语法兼容

【表选择决策规则（必须遵守）】
{从 general.md §【表选择决策规则】复制，固定注入，不可省略}

【通用注意事项】
{从记忆中提取的通用知识，例如：}
- executeQuery 禁止使用 -- 注释，会报错
- tags 提取用 ifly_map_get(tags, 'key_name')，tags_json 不可靠
- 亿级大表 join 注意性能，需按 uid 前缀分片

【SQL 编码规范（强制）】
- 必须使用 CTE（WITH ... AS）结构，禁止嵌套子查询
- UV 口径：先按 uid 分组聚合，再汇总计数，禁止顶层直接 COUNT(DISTINCT uid)
- 分区裁剪：必须显式过滤分区字段
- 数值精度：ROUND(x, 2)
- 最终结果必须 ORDER BY
- PV 计算：GROUP BY 聚合配合 COUNT(1)
- SQL 中禁止使用 -- 注释

【工作步骤】

**知识库检索（主 Agent 已完成，无需重复调用 searchSqlGuides）**
主 Agent 已按 3~5 个核心关键词检索知识库，结果已注入【记忆上下文】。若记忆上下文中有高质量命中（≥80% 匹配），直接基于参考 SQL 改写，跳过 searchTables 步骤。

**操作码验证（涉及 opcode 时必须）**
若需求涉及操作码（FTxxxxx），在用操作码查数据前，必须先执行：
`describeOpcode(opcode)` — 验证该操作码当前是否仍然有效。
操作码约每半年迭代一次，记忆中的编号可能已失效。

**第一步：搜索相关表（自适应预算）**
根据记忆上下文命中质量，searchTables + searchTablesByColumn + describeTable + searchEnumByColumn 合计调用上限：

| 命中等级 | 判断标准 | 搜索调用上限 |
|---------|---------|------------|
| 高质量命中 | 需求 ≥80% 匹配，表名/操作码与记忆一致 | ≤ 5 次 |
| 中质量命中 | 场景相似但口径细节不同 | ≤ 10 次 |
| 未命中 | 无相关结果 | ≤ 20 次 |

超出预算后必须停止搜索，基于已有信息编写 SQL 并执行。

**第二步：编写并执行 SQL**
严格遵循编码规范，executeQuery 执行，失败最多重试 2 次。

【输出格式】
严格按以下格式输出：

--- SQL ---
{最终执行成功的完整 SQL}
--- RESULT ---
{执行结果的完整 JSON，包含 columns 和 rows}
--- COLUMNS ---
{列名列表，逗号分隔}
--- ROW_COUNT ---
{结果行数}
```

**关键：subagent 只收到原始需求、记忆上下文和通用规范，不收到主 Agent 预查的表结构或字段信息。**

**派发后立即记录两个 Agent 的 ID**，格式如下（用于后续 SendMessage）：
```
agent_a_id = <Agent A 返回的 agentId>
agent_b_id = <Agent B 返回的 agentId>
```

### 用户口径修正（修正场景专用）

**当用户在查询过程中补充或修正口径时，禁止重新派发新 Agent。**

判断逻辑：
```
用户说"用FT52059作为下载" / "换成XX表" / "条件改为YY"
→ 这是口径修正，不是全新需求
→ 用 SendMessage 继续已有 Agent，不新建
```

**操作步骤**：
1. **选取 Agent 的标准**：优先选先返回成功结果的 Agent。若两个均已返回（均成功或均失败），固定选 Agent A。用 `SendMessage(to: agent_a_id 或 agent_b_id)` 发送修正说明。
   ```
   用户确认了以下口径修正：
   - {修正内容，原文转述}
   请基于你已探索到的表结构和字段，直接修改 SQL 并重新执行，无需重复搜索。
   输出格式保持不变（--- SQL --- / --- RESULT --- / --- COLUMNS --- / --- ROW_COUNT ---）
   ```
2. 收到修正结果后，继续执行第三阶段（结果比对）

**何时才派发新 Agent**：
- 用户提出与原需求完全不同的新查询
- 两个 Agent 都已超时或报错无法继续

### 第三阶段：结果比对（主 Agent）

从两个 subagent 返回中提取 SQL 和结果，**先做维度诊断，再做数值比对**：

#### 3a. 维度分歧诊断（优先于数值比对）

先检查两份 SQL 的**维度和粒度**是否一致：
- 行数差距 > 50% → 大概率是维度/粒度不同，不是计算错误
- 分组字段不同（如一个按来源分组、一个不分组）→ 语义分歧，非数值分歧
- 过滤条件不同（如一个过滤社区帖，一个不过滤）→ 业务范围分歧

**维度分歧处理**：
- 不进入仲裁，直接用 AskUserQuestion 向用户展示两种口径，请用户确认采用哪种
- 收到用户确认后，用 SendMessage 通知对应 Agent 修正，另一个 Agent 同步修正

#### 3b. 数值比对（维度一致时执行）

1. **列名一致** — 列名集合相同（忽略中英文别名差异，按位置对应比对值）
2. **行数一致** — 行数完全相同
3. **数据一致** — 按第一列排序对齐后，每行每列值完全相同

- **一致** → 进入第四点五阶段（技术合理性检查）
- **不一致** → 进入第四阶段（仲裁）

#### 降级策略

| 情况 | 处理方式 |
|------|---------|
| Agent A 成功，Agent B 失败/超时 | 降级为单 Agent 模式，直接进入后验层，展示时注明"单 Agent 结果（Agent B 执行失败：{原因}）" |
| 两个均失败 | 不展示结果，向用户说明失败原因并引导澄清（需求描述？日期范围无数据？表结构变化？） |

### 第四阶段：仲裁重试（最多 3 轮）

1. **差异分析** — 对比两份 SQL，找出差异点（表选择、过滤条件、聚合口径、JOIN 逻辑）
2. **口径纠正** — 根据记忆和业务逻辑判断正确口径，必要时调用 MCP 验证
   **纠正说明的信息边界**：
   - ✅ 允许包含：字段名、枚举值、分区字段名称
   - ❌ 禁止包含：完整 WHERE 子句、JOIN 条件、完整 SQL 片段
3. **重新派发** — 追加口径纠正说明后重新并行派发
4. 回到第三阶段比对
5. **超过 3 轮** — 展示两份 SQL + 结果 + 差异分析，让用户决定

### 第四点五阶段：技术合理性检查（展示前必须执行）

收到 subagent 结果后，主 Agent 在展示前自动检查以下条件：

| 检查项 | 触发条件 | 处理方式 |
|--------|---------|---------|
| 零行结果 | ROW_COUNT = 0 | 拦截展示，分析原因（枚举值拼写？分区无数据？过滤条件过严？），用 AskUserQuestion 让用户选择：回溯修正 or 仍然展示 |
| NULL 率异常 | 核心指标列 NULL 占比 > 30% | 警告提示，可能是字段名错误或 ifly_map_get key 写错，继续展示但附警告 |
| UV 数量级过大 | UV 结果 > 5000万 | 警告提示，可能误用了 PV 口径（讯飞输入法活跃用户量级参考上限），继续展示但附警告 |
| 转化率异常 | 转化率 > 100% 或 < 0.01% | 警告提示，检查分子分母是否对应同一口径/同一时间范围，继续展示但附警告 |

**全部通过** → 直接进入第五阶段展示结果。
**零行结果** → 拦截，等待用户决策。
**其他命中** → 展示警告后继续展示结果。


### 第四点七阶段：业务合理性校验（有历史基准时执行）

若本次查询结果在 `./memory/biz/<业务>/history.md` 中有对应历史基准，自动对比：

```
计算偏差 = abs(本次值 - 历史基准均值) / 历史基准均值

偏差 < 30%  → 通过，展示时附注"与历史基准偏差 X%，在合理范围内"
偏差 30~80% → 黄色警告，提示用户确认是否合理（可能有业务波动）
偏差 > 80%  → 红色警告，建议回溯检查口径，并展示历史基准数据作为参考
```

对已在 history.md 中标注"波动较大"的月份，偏差阈值放宽一倍（60% / 160%）。

无对应历史基准时跳过此阶段。

**history.md 更新触发规则**：每季度首次查询该业务全站月度数据时，主 Agent 自动提示：
> "当前 history.md 最新数据为 XXXXXX，距今超过 3 个月，是否更新历史基准？"
> 用户确认后，将本次结果追加（保留最近 12 个月，删除更早数据）。

### 第五阶段：展示结果

1. **验证状态** — "双 Agent 验证通过（第 N 轮一致）"
2. **SQL 展示** — 两份 SQL 内容一致时只展示一份；有实质差异时（如一个用聚合表、一个用操作码明细）展示两份并说明差异点
3. **执行结果** — 格式化表格
4. **查询口径说明** — 关键筛选条件和业务逻辑

### 第六阶段：记忆评估与维护

查询完成后执行两个子步骤。详见 [memory-guide.md](references/memory-guide.md)。

#### 6a. 新知识评估

逐项检查以下维度，任一命中则建议写入：

| 维度 | 命中条件 | 写入目标文件 |
|------|---------|------------|
| 口径发现 | 确认了非显而易见的指标计算方式 | biz_*.md |
| 表/字段映射 | 业务概念 → 表名/字段名的对应关系 | biz_*.md |
| 操作码关联 | 新发现 opcode ↔ 业务场景对应 | biz_*.md |
| 枚举/Tag 含义 | 字段枚举值的业务含义，尤其与字面不符时 | biz_*.md |
| 仲裁经验 | 两 Agent 不一致的根因有泛化价值 | biz_*.md 或 general.md |
| 性能教训 | 超时/溢出且解决方案可复用 | general.md |
| 工具踩坑 | MCP 工具行为与预期不符 | general.md |

**写入要求**：biz_*.md 中的条目需足够具体，包含：表名、字段名、枚举值、操作码等原始信息，使 subagent 下次可直接跳过搜索步骤复用。

**全部未命中** → 回复末尾一句话说明"本次无新增可复用经验"

**命中任一** → 按知识类型执行对应写入策略：

| 知识类型 | 写入方式 |
|---------|---------|
| 踩坑记录（工具 bug、枚举陷阱、表分区问题） | **自动写入**本地，无需确认 |
| 口径类（UV/PV 定义、指标计算逻辑、转化口径） | 展示摘要 + **用户确认**后写入 |
| 操作码关联（新发现的 opcode ↔ 业务场景映射） | 展示摘要 + **用户确认**后写入 |

口径类/操作码类确认：**必须调用 `AskUserQuestion` 工具**向用户提问，不得仅以文字展示：

```
AskUserQuestion(
  question="发现可复用知识：\n**类型**：口径\n**内容**：{1-2句简述，含表名/字段/操作码等关键信息}\n是否写入本地记忆？",
  options=["是", "否"]
)
```

用户选"是"后写入，并同步更新 MEMORY.md 索引。

**步骤2（需征求同意）：同步到中心知识库（本地写入完成后执行）**

**前置：中心知识库去重检查（必须先执行，再问用户）**

调用 `searchSqlGuides`，用本次知识的核心关键词搜索（操作码编号、表名、业务名，2-3 个词）：

| 命中情况 | 处理方式 |
|---------|---------|
| 相似度 ≥ 80%（表名/操作码/口径均一致） | **跳过同步**，告知用户「中心知识库已有类似条目：{标题}，无需重复提交」 |
| 命中但有关键差异（如数据起始时间不同、字段变更） | 展示差异点，询问用户是否**覆盖更新**已有条目 |
| 未命中 | 进入下方正常同步流程 |

**未命中时，调用 `AskUserQuestion` 工具询问**：

```
AskUserQuestion(
  question="以上口径已写入本地记忆，中心知识库未发现重复条目。是否同步到中心知识库供团队共享？\n内容：{1-2句摘要}",
  options=["同步", "跳过"]
)
```

用户确认后，调用 `mcp__iflytek-sql-gateway__saveSqlGuide` 保存。

**理由**：中心知识库为团队共享，SQL 口径可能存在业务歧义或尚未最终确认，须经用户审核后再共享，避免传播错误口径。重复提交会导致知识库膨胀、检索干扰，去重检查是同步前的强制门控。

**仅在以下情况跳过征求**：
- 用户在本轮对话中已明确说"直接保存"或"自动同步"
- saveSqlGuide 调用失败，向用户说明并询问是否重试

#### 6b. 已有记忆回顾（被动维护）

如果本次查询过程中发现已有记忆存在问题，顺手修正：

- **口径不符** → 立即更新记忆中的口径
- **模板失效** → 标记 `[⚠️ 待验证]` 或直接修正
- **冗余条目** → 合并到最相关的文件
- 文件数接近上限（≥8）时提醒用户，并建议合并或淘汰低频文件

## 注意事项

- subagent 使用 `subagent_type: "general-purpose"` 获得 MCP 工具访问权限
- 两个 subagent 必须在**同一条消息**中并行派发
- **主 Agent 在第一阶段禁止调用 MCP 查表工具**（searchTables、describeTable 等），但可调用 searchSqlGuides 做知识库检索（第4步）
- subagent prompt 中**不包含任何具体表名、字段名、表结构**
- 仲裁阶段主 Agent 可调用 MCP 验证口径，但纠正说明只描述业务口径，不直接给 SQL
